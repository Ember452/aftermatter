# AfterMatter 项目设计文档（PRD）

状态: 定稿（设计阶段） | 版本: v1.0 | 层级: 阶段 1 | 架构与契约详见 [architecture/](architecture/INDEX.md)

---

## 1. 背景与问题

AI 编码 Agent（Claude Code、Codex、Cursor 等）改代码很快，但围绕它们的工作流往往是薄弱环节，
且**只审查最终 diff 会系统性遗漏这些问题**：

| 痛点 | 表现 |
|------|------|
| 🎯 目标模糊 | Agent 信心十足地解决了错误的问题 |
| 🧭 执行路径随意 | 工作走在无人能复现的路径上 |
| ✅ "能跑"没有证据 | 验证不完整或缺失，"Agent 说测试过了"无从考证 |
| 🚀 速度压过门禁 | 审查与交付检查被绕过 |
| 🧠 经验不沉淀 | 同样的摩擦在下一个任务反复出现 |

2026 年市场信号：泛化 Agent 可观测（tracing/cost/spend）已是红海（LangSmith、AgentOps、
mission-control 6.3k★ 等），但**"面向用户日常工作流的证据驱动体检 + 统计纵向验证"仍是空白带**——
近乎唯一的同类是 Better Harness（Node/TS，MIT，寄生宿主；其对比能力为主动受控实验，
精确口径见 §4 与 ADR-0009）。

## 2. 产品定位

**一句话**：读你编码 Agent 留下的本地会话与仓库证据，按五维 Agent Work Loop 产出
"每条断言可指回原始字节"的改进发现；不止报告——它起草有界修复，并纵向验证改进是否真的生效。

**品类区隔**（防漂移，重要）：

- ❌ 不是 LLM tracing/observability 工具（不看单次调用/token 流水账）
- ❌ 不是编码 Agent 框架（不执行开发任务）
- ✅ 是 Agent 工作流的**审查与改进闭环**基础设施（diff 背后的系统学）

## 3. 目标用户与核心场景

| 用户 | 场景 | 关键诉求 |
|------|------|---------|
| 重度 AI 编码个人开发者 | 本地跑一次体检 / 挂 cron 每周自动分析 | 免费或低成本、隐私安全、报告可信 |
| Agent 平台/工程负责人 | 团队聚合视图：谁的 harness 在拖后腿、改进是否收敛 | 只上传结论不传原始会话、趋势可比 |
| CI/CD 运维 | PR 门禁：新改动引入的工作流退化要被拦 | 确定性、可脚本化、低误报 |
| 开源社区用户 | `pip install aftermatter` + 宿主内一句话体检 | 零门槛试用、可读报告 |

## 4. 竞品格局与我们的 whitespace（2026-09 调研）

| 层级 | 代表 | 结论 |
|------|------|------|
| 通用 Agent 可观测 | LangSmith / AgentOps / Langfuse / mission-control | 红海，**主动放弃，永不进入** |
| "harness" 主流语义（执行框架） | awesome-agent-harness 及各对比 | 词义歧义 → 名字不含 harness，仅进 tagline |
| 会话失败模式分析 | Failproof AI（商业闭源） | 方向被验证，但无本地自托管开源形态 |
| 五维证据体检 | **Better Harness（原版）** | 唯一同类；寄生宿主（无自带引擎）；修复与纵向验证在其架构图中是 Repair→Validate→Record 的**人驱动流程与模型概念**；其 experiment/compare 系统（其 ADR-0004/0005，packages/harness，已实现）是面向 harness 开发的**主动受控实验**（matched-pair 规则地板，非统计显著性检验），而报告链路的验证证据仍为转述级；roadmap 无无人值守方向 → 我们把**用户工作流的被动纵向闭环**做成机制（ADR-0009） |
| 声称性验证 | reverify(942★) / groundproof | 佐证"模型提议、工具裁决"理念，但是通用组件不是工作流体检 |

## 5. 差异化主张（全部要能写进简历、经得住代码级追问）

1. **双大脑**：同一确定性证据内核，大脑①寄生宿主（Skill+MCP，零 API 成本）；
   大脑②自带多 Provider LLM 引擎（cron/CI 无人值守）。原版只有①。
2. **闭环到"修复 + 纵向验证"**：有界修复起草 → 白名单执行 → 干预台账 →
   后续可比较 Episode 的统计显著性检验（bootstrap / CUSUM 变点），把"我以为改进了"
   变成"证据证明改进了"。注：原版已有 finding-bound repair 流程与 later-validation
   模型概念（诚实校准，勿说"原版没有闭环"），但执行靠宿主会话中的人驱动，且验证
   停留在状态记录——我们把它升级为无人值守、可统计复验的机制。
   校准注记（ADR-0009）：原版已有主动受控实验系统及其 matched-pair 规则证据地板，
   但其决策是阈值制非统计显著性检验；bootstrap/CUSUM/置信区间与被动工作流纵向归因
   仍是我们的增量，两路线互补不互斥。
3. **执行级证据引擎**：不信任转述——沙箱重放复跑测试/lint/build，
   blast radius 静态影响面 × 实际测试覆盖面 → 找验证空洞。限定（ADR-0009）：我们做的是
   **报告链路中对 claimed 命令的沙箱复跑**（claimed_ok→replay_ok，含工作树完整性收据）；
   原版的 checkpoint lane 重放属主动实验产品面，两者不互相替代。
4. **Local-first 隐私**：原始会话永不出机器，上传的是脱敏后的结构化 findings。

## 6. 功能需求

优先级：P0 一期必须 / P1 一期尽力 / P2 二期。验收标准全部可自动化或可演示。

### FR-A 证据采集（collectors）

| ID | 需求 | 优先级 | 验收 |
|----|------|:---:|------|
| A1 | Claude Code JSONL 会话适配器（~/.claude/projects/） | P0 | fixture 解析正确率 100%，字段映射有单测 |
| A2 | Codex CLI 会话适配器 | P0 | 同上 |
| A3 | Cursor / Qoder 适配器 | P1 | 同上 |
| A4 | 仓库证据扫描：AGENTS.md/CLAUDE.md、测试布局、CI workflow、git 历史、hooks/skills 资产清单 | P0 | 输出结构化 RepositoryEvidence |
| A5 | 增量索引：内容哈希未变的会话不重读（内容寻址缓存） | P1 | 二次采集耗时 < 首次 20%（基准测试） |
| A6 | 流式解析 GB 级 JSONL，内存上限可配置 | P1 | 1GB 会话内存占用 < 256MB |

### FR-B Episode 重建（episodes）

| ID | 需求 | 优先级 | 验收 |
|----|------|:---:|------|
| B1 | 30min 时间缺口 + 新任务 prompt 双规则切分 TaskEpisode | P0 | 黄金样例集上切分一致 |
| B2 | 行为/验证/摩擦事件分类（edit、test/lint/build、权限拒绝、失败重试、用户纠错） | P0 | 分类器单测全覆盖 |
| B3 | 可比较性特征：任务类型、规模、工具序列形态、model 版本记录 | P0 | 特征进 Episode schema |
| B4 | 每个事实带 ERef 证据指针，断言可回溯原始字节 | P0 | 引用解析失败即该事实不可用 |

### FR-C 分析引擎（analysis，大脑②的多 Agent 编排）

| ID | 需求 | 优先级 | 验收 |
|----|------|:---:|------|
| C1 | 三证据专家 Agent（会话/项目/资产）并行、只读、lane 隔离、互相不可见结论 | P0 | 越界断言被结构拒绝（协议级） |
| C2 | Lead Judge 裁决流水线：ERef 核验→合并(四元组规则)→保留异议→定级→分数独立于数量 | P0 | 黄金集上定级与人工标注一致率 ≥80% |
| C3 | 五维 15 检查评估 + 7 证据状态 + 证据状态决定评分天花板 | P0 | 违反天花板的分数被校验器拒绝 |
| C4 | 预算守卫：每角色 token/成本上限，超限降级 deterministic-only 报告 | P0 | 超限注入测试可复现降级 |
| C5 | 双通道评分交叉验证：确定性基线分 × LLM 分冲突 → 置信度降级 | P1 | 冲突用例集通过 |
| C6 | 对抗测试套件：注入假证据/伪造"已验证"/刷分 CI，系统必须拦截 | P1 | 拦截率进 CI 门禁 |
| C7 | 大脑①：MCP server 暴露证据工具 + SKILL.md 宿主寄生入口 | P0 | Claude Code/Qoder 内一句话完成体检 |

### FR-D 修复与执行验证（repair + 沙箱）

| ID | 需求 | 优先级 | 验收 |
|----|------|:---:|------|
| D1 | Repair Agent：仅对白名单目标（AGENTS.md、CI 配置、缺测试清单等）起草有界修复方案 | P0 | diff 越界 = 直接拒绝，白名单外零写入 |
| D2 | 修复 dry-run/apply 两阶段，apply 需显式确认（非交互模式必须 --yes） | P0 | 无确认写入路径不存在 |
| D3 | Verifier：Docker 断网沙箱重放复跑（测试/lint/build），产出结构化结果（含工作树完整性收据，ADR-0009） | P1 | 声称已通过但复跑失败 → finding 自动升级；无收据的复跑标 contextual 不得回填 replay_ok |
| D4 | blast radius（tree-sitter 静态影响面）× 测试映射归因 → 验证空洞发现 | P1 | 改动核心只跑边缘测试的 fixture 被捕获 |
| D5 | 容器池与资源限额（CPU/内存/超时/断网默认） | P2 | 限额生效有集成测试 |

### FR-E 纵向验证（longitudinal）——技术皇冠

| ID | 需求 | 优先级 | 验收 |
|----|------|:---:|------|
| E1 | SQLite 历史库：Bundle/Finding/Ledger 持久化，schema 版本化迁移 | P0 | 迁移测试前后版本兼容 |
| E2 | InterventionLedger：修复应用事件流，关联 finding_id | P0 | 台账完整可审计 |
| E3 | 可比较 Episode 匹配：结构化特征 + 向量嵌入双通道，可比性置信度输出 | P1 | 黄金对（可比/不可比）判别准确率 ≥85% |
| E4 | 混杂控制（单轴归因，ADR-0009）：恰一处理轴不同才可归因；多轴 → descriptive-only 无 verified 资格；零轴 → 记为噪声测量 | P1 | 三态注入行为全部正确，理由机器可读 |
| E5 | 小样本统计：bootstrap 置信区间 + CUSUM 变点检测；显著才升 `verified`，不显著保持 `open` 并说明缺多少样本；最小可检效应参照噪声地板（无干预期可比对的 run-to-run 变异基线） | P1 | 模拟数据上假阳性率 <5%；噪声地板估计存在且被 Verdict 引用 |

### FR-F 报告（report）

| ID | 需求 | 优先级 | 验收 |
|----|------|:---:|------|
| F1 | 自包含 HTML + Markdown 双格式；五维概览、优先级发现、证据简报、rejected 附录 | P0 | 渲染 schema 校验通过 |
| F2 | 证据缺口显式化：partial/unavailable 三态如实呈现，不臆断评分 | P0 | 无证据处显示 Unobserved |
| F3 | 历史趋势视图（本地 Web 只读面板，二期做满） | P2 | 一期出静态趋势图即可 |
| F4 | 比较边界强制声明：任何趋势/纵向比较输出必须携带机器可读的 Comparability+Verdict（可比性、被排除的混杂、是否因果），禁止裸 Δ 分数 | P0 | 无边界声明的比较块渲染器拒绝出图（原版仅一行免责文本，我们升级为机制） |

### FR-G 服务端（serve + daemon）——一期最小骨架

| ID | 需求 | 优先级 | 验收 |
|----|------|:---:|------|
| G1 | 本地 daemon：定时驱动大脑②分析，产出 findings | P1 | cron 式周期任务可停可续 |
| G2 | 上传管道：仅 findings + 元数据（多级脱敏），幂等上报（idempotency key） | P1 | 重传不产生重复行 |

| G4 | 多租户隔离、配额、队列、限流 | P2 | 二期验收 |

### FR-H 非功能需求

| ID | 需求 |
|----|------|
| H1 | 隐私：所有出机数据过脱敏管道（路径归一化、prompt 摘要化、secret/PII 剥离），脱敏有可验证测试 |
| H2 | 成本：大脑②每次运行有明确 token/费用预算并在报告中如实记录 |

## 7. 非目标（明确不做，防 scope 漂移）

- ❌ 通用 LLM tracing / token 流水账大盘（红海，见 §4）
- ❌ 模型能力评测榜单（不做 "GPT vs Claude"，混杂太多且非本品类）
- ❌ 自己执行开发任务的 coding agent（我们是审查者不是执行者）
- ❌ 一期不做 GUI/桌面端与证据浏览器 UI（F5 仅机制预埋）；服务端一期只到 G3 骨架
- ❌ 不承诺对宿主私有格式的"永不过期"兼容——格式漂移风险公开记录在案（§10-R1）

## 9. 成功指标（发布后度量，也是简历量化数据来源）

- 解析器：4 宿主格式覆盖数；单宿主解析正确率（对黄金集）
- 可信性：ERef 核验通过率；对抗测试集拦截率（目标 100% 核心用例）
- 闭环：修复建议采纳率；`verified` 状态 finding 占比（纵向验证真跑通的证据）
- 增长：GitHub Star、pip 月下载、报告分享数、外部 issue/PR 数
- 成本：单次完整分析平均 token 费用（透明化本身是卖点）

## 10. 风险与对策

| 风险 | 等级 | 对策 |
|------|:---:|------|
| R1 宿主会话格式漂移（私有格式逆向维护税） | 高 | 版本探测 + 解析失败显式报错不猜；适配器独立子包降低爆炸半径；README 公开此边界 |
| R2 纵向验证统计效力不足（样本小） | 高 | 输出"证据不足"是正常态而非失败；显式报告缺多少样本；先做仓库内自比而非跨仓库 |
| R3 LLM 幻觉污染发现 | 中 | 结构性防线（ERef 强制核验 + 基线分交叉 + 反作弊集），见 architecture/overview.md §6 |
| R4 与原版功能撞车被比较 | 中 | 差异化三点（§5）进 README 首屏；承认灵感来源并给贡献路径 |
| R5 单人项目战线过长 | 中 | 里程碑串行、每段有独立可展示物；M2 前完全不依赖 LLM 层 |
| R6 沙箱重放的安全事故 | 中 | 默认断网、限额、只读挂载、超时硬杀；D5 前修复闭环只 dry-run 不 apply 执行类操作 |
