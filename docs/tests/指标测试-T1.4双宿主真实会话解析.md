# 指标测试 — T1.4 双宿主真实会话解析

状态: 已实测（2026-09-22） | 对应: DEVELOPMENT-PLAN §5 M1 第 5 项、FR-A2、T1.4 | 关联: ADR-0016、`指标测试-T1.3真实会话解析.md`

## 目的

T1.4 引入第二个宿主（Codex CLI）。验收要回答的不是"能不能解析 Codex"，而是
**同一套 L0 契约（`RawEvent`/`ERef`/`ParseStats`）换一家宿主还成立吗**。因此两个宿主用同一
脚本、同一计数器口径各跑一遍真实会话，并把结果并排记录。

## 步骤

```
uv run python .aftermatter/real-parse.py claude
uv run python .aftermatter/real-parse.py codex
```

脚本用包 API（`discover` → 逐 `SessionRef` `parse`），只输出聚合计数与原因分布；
文件身份为 `sha256(文件名)[:8]`，不输出 prompt 原文、命令原文或真实绝对路径。
脚本与其输出都在 gitignored 的 `.aftermatter/` 下，不入库。

## 结论

1. **M1 第 5 项在第二个宿主上通过**：Codex 3/3 会话入候选、0 文件失败、`unparsed = 0`。
   两家的 `unparsed` 都是零基线，说明映射表覆盖了本机可见的全部 type 词表。
2. **契约成立，但被实测压出三处宿主差异**（全部写进 `collectors.md` 的宿主差异表）：
   Codex 判别是 `type` × `payload.type` 两层；`session_id`/`cwd`/`model` 不逐行携带，
   适配器必须 carry-forward；`arguments` 是 JSON 字符串需二次解析。
   模型层（`RawEvent`/`ERef`/`ParseStats`）未因第二家宿主改动一个字段。
3. **双计风险被数据证实并挡住**：`duplicate_of_response_item` 实测 8 条，与探雷阶段
   `agent_message` 5 + `user_message` 3 完全吻合。若不做这条忽略，Codex 的
   `user_prompt`/`assistant_message` 会被重复计数，下游"验证配对率"等指标当场失真。
4. **`result_ok` 在 Codex 侧不可观测**（`output` 是纯字符串，24/25 不带退出码），
   适配器一律留 `None` 而非猜成败。代价要写清楚：T1.6 的 `claimed_ok` 对 Codex 会话
   只能来自命令文本与后续 git 证据，不能来自工具回执——这会影响该宿主在
   `change-validation` 维度上的证据天花板，属于产品的真实边界而非实现缺陷。
5. **`lifecycle` 首次有真实证据**（9 条：`session_meta` 3 + `task_started` 3 +
   `task_complete` 2 + `turn_aborted` 1）。`permission_decision` 与 `hook_event`
   两家宿主实测都是 0，映射表保留其 kind 但不虚构来源。
6. 副作用验证：本会话把行读取统一到 `collectors/jsonl.py` 后，Claude 侧真实数据结果与
   T1.3 记录逐项相同（465 / 275 / 190 / 0 / 7），说明重构行为不变。
7. **样本局限**：各只有一台机器、少量会话（465 + 138 行）、近一周本机使用；Codex 侧的
   `outer/inner` 组合仅覆盖本机出现过的那些 `payload.type`，未观测到的组合没有映射规则，
   一旦落到就进 `unparsed`——那正是这条计数器存在的目的，不要去预防性猜写它。
